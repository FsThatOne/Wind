# 存档系统

> **Status**: Designed
> **Author**: user + systems-designer + gameplay-programmer
> **Last Updated**: 2026-06-03
> **Implements Pillar**: Pillar 2 — 每个选择必须有重量，包括错过的

## Overview

存档系统是《孤山遗剑》叙事承诺的技术载体。它通过序列化和反序列化两种操作，将游戏世界的完整状态写入磁盘并在需要时精确还原——使得"不可撤销的抉择"得以在技术层面真正成立。

该系统维护任意数量的存档槽，每个槽包含一份独立的完整游戏状态快照：角色功力与属性、武学获取情况、心境双轴位置（影响 5 结局）、每段感情线的关系节点与承诺选择、对话分支历史、暗号/书信发现记录、同伴离队代办进度、主线章节推进节点、自然日历状态，以及全局设置。

存档文件采用 JSON 格式生成，并以 AES 对称密钥加密落盘（防止简单篡改，不追求反逆向）。在开发构建中提供明文 JSON 旁路，便于调试和 schema 版本迁移。

存档系统不持有游戏逻辑——它只记录状态。所有游戏系统在需要持久化时向存档系统注册数据序列化器；在加载时，存档系统将数据块分发给对应系统的反序列化器，各系统自行恢复运行状态。这种"数据分发"模式使 schema 在各系统独立迭代时保持可扩展性，符合概念文档中"早期建立可扩展的存档 schema"的技术风险缓解策略（T3）。

## Player Fantasy

玩家不会察觉存档系统——这是它成功的标志。

他们感受到的，是离开游戏数天后回来，一切还在——白苓等待的眼神还停在那个转角，那封没打开的信还压在案头，杀仇人之前那一声"手下留情"仍然是他们没有说出口的话。

存档系统让 Pillar 2（每个选择有重量）不停留在设计哲学层面。它是承诺的基础设施：玩家在心境选择"执念"那一刻，不会因为游戏重开、崩溃、换台电脑而被撤销。这个重量是真实的，因为技术上它确实是。

**玩家幻想的具体形式**："这款游戏记住我所有的选择" —— 不只是剧情选项，还有每一次"没有做"的事：没有追的支线、没有说出口的承诺、没有及时澄清的误会。这些"不作为"与"作为"一起被存档，一起构成玩家的江湖。

## Detailed Design

### Core Rules

1. **存档槽模型**：最多 **10 个手动存档槽** + 1 个滚动自动存档槽（`autosave`）。自动存档覆盖上一个自动存档，不新增槽。手动存档槽以 `slot_01` ~ `slot_10` 命名；任意槽可被玩家覆盖或删除后空出。

2. **手动存档时机**：玩家可以在任意时刻通过暂停菜单触发手动存档，以下状态除外：
   - 战斗进行中（`CombatState.Active`）
   - 过场动画 / CG 播放中（`CutsceneState.Playing`）
   - 锁定对话序列中（`DialogueState.Locked`，由剧情触发，通常为关键剧情节点前后）
   - 存档操作本身进行中（防止并发）

3. **自动存档触发**：以下事件自动触发覆盖 `autosave` 槽：
   - 场景切换完成（新场景加载后）
   - 客栈休息完成（自然日推进节点）
   - 主线章节节点推进后
   - 对话系统完成一次锁定对话序列后

4. **文件格式与加密**：
   - 每个存档槽写入一个 JSON 文件，路径 `user://saves/slot_{id}.sav`
   - 正式构建：以 AES-256 对称密钥加密（密钥内置于可执行文件）
   - 开发构建（`IS_DEV_BUILD = true`）：同时写出明文 `slot_{id}.sav.dev.json` 用于调试
   - 全局设置（音量、分辨率等）单独存储于 `user://settings.cfg`，不加密

5. **数据分发模型（可扩展 schema）**：
   - SaveManager 是全局单例（Godot Autoload），持有所有已注册的系统序列化器
   - 每个游戏系统在初始化时向 SaveManager 注册一对 `(SerializeFunc, DeserializeFunc)`，以系统 key 字符串标识（如 `"character"`, `"mindset"`, `"dialogue"`）
   - 存档时：SaveManager 遍历所有注册器，调用各自的 `SerializeFunc()`，将返回的字典写入存档 JSON 的对应 key
   - 加载时：SaveManager 读取 JSON，将各 key 的字典传递给对应系统的 `DeserializeFunc(dict)`，各系统自行还原运行状态
   - 未知 key（来自更新版本的存档）被忽略，不会导致崩溃（向前兼容）

6. **Schema 版本迁移**：
   - 每个存档文件头包含 `schema_version`（整数）
   - 加载时检查版本：若低于当前版本，顺序应用迁移函数（`Migration_v1_to_v2()` 等）
   - 迁移函数补充新增字段的默认值，不删除旧字段

7. **存档元数据**（用于槽位列表展示）：
   - 时间戳（UTC）
   - 章节名称 / 场景名称
   - 游戏内时间（第几日）
   - 累计游戏时长（秒）
   - 截图缩略图（128×72 px PNG，base64 嵌入 JSON 或独立文件）

### States and Transitions

| 状态 | 描述 | 可进入的下一状态 |
|------|------|----------------|
| `Idle` | 无存档操作进行 | `Saving`, `Loading`, `Blocked` |
| `Saving` | 序列化 + 文件写入中（异步） | `Idle`（成功）, `SaveFailed` |
| `Loading` | 文件读取 + 反序列化中（异步） | `Idle`（成功）, `LoadFailed` |
| `Blocked` | 当前场景状态禁止存档（战斗/过场/锁定对话） | `Idle`（阻断条件解除） |
| `SaveFailed` | 写入失败（磁盘满 / 权限拒绝） | `Idle`（玩家确认错误对话后） |
| `LoadFailed` | 读取失败（文件损坏 / 解密失败） | `Idle`（玩家确认 + 提供备份恢复选项） |

### Interactions with Other Systems

| 系统 | 交互方向 | 接口 / 数据 |
|------|---------|------------|
| 角色属性 / 功力 | 下游 → 存档 | 注册序列化器，导出：各属性值、总功力、当前境界 |
| 武学组合 | 下游 → 存档 | 注册序列化器，导出：已解锁武学列表（层级：残卷/拓本/完本/真传/批注版）、当前装备武学、各批注版的 annotation_mult 与来源标识 |
| 心境双轴 | 下游 → 存档 | 注册序列化器，导出：`resolve`（执念↔释怀）、`worldly`（入世↔出世）、`morality`（善恶五档，-2~+2）、`reputation`（声望值）、`current_zone`（当前区域状态枚举）、`shift_log`（位移历史日志，可选，用于结局判定） |
| 对话系统 | 下游 → 存档 | 注册序列化器，导出：所有对话标志（曾做过的选择 ID 集合）、洞察揭示历史 |
| 感情系统（未设计） | 下游 → 存档 | 预留 key `"relationships"`，注册时机由该系统 GDD 定义 |
| 主线叙事/章节（未设计） | 下游 → 存档 | 预留 key `"chapter_progress"` |
| 自然日/体力（未设计） | 下游 → 存档 | 预留 key `"calendar"` |
| 物品/道具（未设计） | 下游 → 存档 | 预留 key `"inventory"`，导出背包物品列表（物品 ID + 数量） |
| 所有 UI 系统 | 存档 → 上游 | 读取元数据渲染存档槽位 UI；SaveManager 发布 `SaveStarted` / `SaveCompleted` / `LoadCompleted` 信号供 UI 监听 |

## Formulas

存档系统无核心数学公式。以下为两个边界定义：

**F1. 存档截图缩略图分辨率**

`thumbnail_resolution = 128 × 72 px`

| 变量 | 值 | 说明 |
|------|----|----|
| 宽度 | 128 px | 约为 1280px 宽度屏幕的 1/10 |
| 高度 | 72 px | 保持 16:9 比例 |
| 格式 | PNG | 无损，嵌入 base64 或独立 .thumb 文件 |

此尺寸在存档槽 UI 中可清晰辨认场景，文件体积 ≤ 8KB（加密后），不显著增大存档包体。

**F2. Schema 版本号**

`schema_version += 1`（每次存档格式发生破坏性变更时手动递增）

| 变量 | 类型 | 说明 |
|------|------|------|
| `schema_version` | int, 起始=1 | 嵌入每个存档文件的 JSON 头 |
| `current_schema_version` | int, 编译时常量 | 代码中的当前版本 |

加载时：`if saved_version < current_schema_version → 顺序执行迁移函数`。

## Edge Cases

- **如果磁盘写入失败（磁盘满 / 权限拒绝）**：存档操作回滚（不写入半成品文件），向玩家展示错误对话框，提示磁盘空间不足或路径权限问题。游戏状态不中断，玩家可继续游玩。

- **如果自动存档触发时玩家恰好在手动存档**：自动存档排队等待，直到手动存档完成后执行；不并发写入同一文件。

- **如果加载的存档文件解密失败（密钥不匹配 / 文件损坏）**：向玩家展示"存档文件已损坏"对话框，提供"加载上一个自动存档"或"取消"选项。不静默崩溃。

- **如果存档的 `schema_version` 高于当前代码版本**（玩家从未来版本降级回旧版）：拒绝加载，提示"此存档需要更新版本的游戏"，不执行迁移（向后兼容不保证）。

- **如果一个下游系统未注册序列化器就触发了存档**：该系统的 key 在 JSON 中缺失；加载时该 key 不存在，系统使用默认值初始化。设计者必须确保所有有持久化需求的系统都在初始化时完成注册。

- **如果玩家在锁定对话序列中尝试打开存档界面**：界面显示但"存档"按钮变灰并显示提示"当前场景不允许存档"，不触发存档操作。

- **如果玩家在战斗中崩溃（强制关闭游戏）**：战斗中不触发任何存档，玩家下次启动时从最后一次自动存档恢复（战斗前）。等价于"强制死亡"，与"战斗失败回到上次客栈休息"逻辑一致。

- **如果截图捕获失败**（分辨率不兼容 / API 异常）：存档正常完成，缩略图使用占位图（黑底 + 章节名文字）。截图失败不阻断存档流程。

- **如果玩家尝试在 10 个槽全部占用时新建存档**：存档 UI 不允许"新建"操作，提示"存档槽已满（10/10）"，强制要求玩家先选择一个已有槽覆盖或删除。不允许超出上限创建第 11 个槽。

- **如果玩家删除所有手动存档且自动存档也不存在**：进入游戏加载界面时，"继续游戏"入口隐藏，只显示"新游戏"。不崩溃，不展示空槽位列表。

## Dependencies

### 硬依赖（此系统运作所需）

无。存档系统是 Foundation 层，零上游依赖。

### 被依赖（下游系统依赖此系统）

| 系统 | 依赖性质 | 依赖内容 |
|------|---------|---------|
| 角色属性 / 功力 | 硬依赖 | 属性值、境界必须跨会话持久化 |
| 回合制战斗 | 硬依赖 | 战斗进入前状态（HP / 内息 / 武学）由存档恢复 |
| 武学组合 | 硬依赖 | 武学解锁状态（残片/拓本/完本）、当前装备 build |
| 心境双轴 | 硬依赖 | 双轴坐标决定 5 结局，必须精确持久化 |
| 对话系统 | 硬依赖 | 分支选择标志集合、洞察揭示历史 |
| 敌方 AI | 软依赖 | 仅依赖存档间接恢复的角色状态，AI 本身无持久数据 |
| 感情系统（未设计） | 硬依赖（预期）| 关系节点、承诺状态 |
| 主线叙事/章节（未设计） | 硬依赖（预期）| 章节推进节点标志、支线完成/错过状态 |
| 自然日/体力（未设计） | 硬依赖（预期）| 日历天数、体力值 |
| 物品/道具（未设计） | 硬依赖（预期）| 背包内容（物品 ID + 数量）、已使用/消耗记录 |

### SaveManager 接口规范

SaveManager 向所有下游系统暴露：
- `RegisterSerializer(string key, Func<Dictionary> serializeFunc, Action<Dictionary> deserializeFunc)` — 系统初始化时调用
- `TriggerAutoSave()` — 供外部系统在特定事件后主动触发自动存档

SaveManager 发布信号：
- `SaveStarted` — 通知 UI 显示存档动画
- `SaveCompleted(bool success)` — 通知 UI 隐藏动画 / 显示错误
- `LoadCompleted(bool success)` — 通知所有系统可以读取恢复后的状态

## Tuning Knobs

| 调节项 | 默认值 | 安全范围 | 极端值行为 |
|--------|--------|---------|-----------|
| `max_manual_slots` | 10 | 5–20 | <5 玩家很快填满感觉受限；>20 存档列表 UI 需要分页增加复杂度 |
| `autosave_thumbnail_width` | 128 px | 64–256 px | <64 缩略图无法辨认；>256 存档文件体积显著增加 |
| `autosave_thumbnail_height` | 72 px | 36–144 px | 保持 16:9 比例调整 |
| `schema_migration_timeout_ms` | 500 ms | 100–2000 ms | 超时则跳过迁移并警告（不崩溃） |
| `dev_plaintext_dump` | `true`（开发构建）/ `false`（正式构建） | — | 正式构建中如为 `true` 则安全风险（可读存档）；此值应为编译时常量而非运行时配置 |
| `autosave_delay_after_trigger_ms` | 500 ms | 0–2000 ms | 触发事件后等待延迟再存档（让过场/对话动画先完成一帧）；0 可能导致截图捕获到过渡帧 |

## Acceptance Criteria

- **GIVEN** 玩家在探索场景中打开暂停菜单，**WHEN** 点击"存档"并选择一个空槽，**THEN** 存档文件生成于 `user://saves/slot_{id}.sav`，加载后可完整还原当前场景、角色状态、对话历史。

- **GIVEN** 玩家在战斗进行中打开暂停菜单，**WHEN** 查看存档界面，**THEN** "存档"按钮变灰且显示"当前场景不允许存档"提示，不触发任何文件写入。

- **GIVEN** 存档槽已满（10 个），**WHEN** 玩家尝试新建存档，**THEN** 系统提示"存档槽已满（10/10）"，强制用户选择覆盖或删除已有槽，不创建第 11 个文件。

- **GIVEN** 游戏触发场景切换，**WHEN** 新场景加载完成，**THEN** `autosave` 槽在 500ms 延迟后被覆盖写入，`SaveCompleted` 信号在写入完成后发布。

- **GIVEN** 存档文件的 `schema_version` 低于当前版本，**WHEN** 玩家加载该存档，**THEN** 迁移函数顺序执行，新增字段以默认值填充，存档加载成功，不报错。

- **GIVEN** 磁盘空间不足，**WHEN** 玩家触发存档操作，**THEN** 操作回滚（无半成品文件），玩家看到错误对话框，游戏继续运行不崩溃。

- **GIVEN** 开发构建（`IS_DEV_BUILD = true`），**WHEN** 任意存档触发，**THEN** 同时写出明文 `.sav.dev.json` 文件，正式构建中此文件不存在。

- **GIVEN** 全部存档（手动 + 自动）均被删除，**WHEN** 玩家启动游戏，**THEN** 加载界面仅显示"新游戏"选项，"继续游戏"入口隐藏。

## Visual/Audio Requirements

存档系统本身无独立的视觉或音效内容——它是纯数据层。以下需求由存档系统的状态信号触发，由 UI 系统和音效系统实现：

- **存档进行中**：屏幕右下角显示一个像素风格的"书写笔刷"动画（约 1-2 秒），低调且不遮挡游戏画面
- **存档成功**：笔刷动画渐隐，无额外音效（避免打断沉浸感）
- **存档失败**：动画替换为"墨迹散落"失败图标，配一声低沉的纸张皱起音效，然后弹出对话框
- **加载完成**：无特殊动画（场景淡入淡出由场景管理系统负责）
- **存档槽 UI**：每个槽展示缩略图 + 章节名 + 日期 + 游戏时长；空槽显示"空（可存档）"；自动存档槽用"自动"标签区分

## UI Requirements

- **存档/读档菜单**可从暂停菜单访问，支持键盘（方向键选择槽、Enter 确认、Escape 取消）和手柄（方向键 / A 确认 / B 取消）完整导航
- **槽位列表**：纵向滚动列表，最多展示 5 个槽（含自动存档槽），剩余槽通过滚动访问
- **新建存档**：若有空槽则显示"新建"按钮；若 10 槽全满则"新建"按钮替换为"槽已满"提示
- **覆盖确认**：覆盖已有存档前弹出确认对话框（"覆盖将不可恢复，确认？"），防止误操作
- **删除确认**：同上
- **存档阻断状态**（战斗中等）：存档按钮显示为灰色不可点，选中时显示原因文字

> 📌 **UX Flag — 存档系统**：此系统有 UI 需求（存档/读档槽位列表、存档元数据展示）。Pre-Production 阶段运行 `/ux-design` 为存档菜单创建 UX spec，故事文件应引用 `design/ux/save-load-menu.md`。

## Open Questions

1. **云存档 / Steam Cloud**：v1.0 是否支持 Steam Cloud 同步存档？如果支持，`user://saves/` 路径需与 Steam Cloud 路径对齐，且文件大小需控制（Steam 免费空间有限）。→ 负责人：technical-director，决策时机：Pre-Production

2. **多周目存档继承**：v1.1 规划中的"多周目继承内容"需要存档 schema 支持跨档槽的数据引用（如"周目 2 继承周目 1 的心境位置"）。当前 schema 为独立快照，需要在 v1.1 前扩展。→ 负责人：game-designer，决策时机：Alpha 后期

3. **存档损坏后的备份恢复**：当前 `LoadFailed` 处理提供"加载自动存档"选项，但如果自动存档也损坏呢？是否需要保留最近 2 个自动存档（rolling backup）？→ 负责人：lead-programmer，决策时机：MVP 实现前
