# NPC 状态管理

> **Status**: In Design
> **Author**: user + agents
> **Last Updated**: 2026-06-04
> **Implements Pillar**: Pillar 1 (江湖是活的，不止围绕你而转), Pillar 2 (每个选择必须有重量), Pillar 4 (情感深度优先于内容广度)

## Overview

NPC 状态管理是《风止》的角色世界状态层，负责记录每个重要 NPC 当前“是谁、在哪里、处于什么剧情阶段、是否可交互、与主角的关系处于何种叙事状态”。它不是一个玩家主动操作的界面，而是支撑“活江湖”的基础系统：NPC 不会永远站在原地等待玩家，他们会离场、远行、写信、错过某次会面，也可能在玩家不在场时完成自己的支线或改变对主角的态度。对玩家而言，这套系统的目标不是让他们看见一张状态表，而是让他们相信江湖中的人都有自己的命运；对其他系统而言，它是对话、心境反应、感情线、活江湖事件和误会系统查询 NPC 当前事实的统一来源，避免叙事分支在复杂推进中互相矛盾。

## Player Fantasy

玩家不会意识到自己正在“使用”NPC 状态管理系统。他们感受到的，是江湖并不因主角停步而停步：有人赴约，有人远行，有人因你没有及时赶到而独自处理了一桩事，也有人在重逢时带回一封信、一段传闻、一个误会或一句迟来的解释。NPC 状态管理服务的幻想是：**“这些人不是任务牌，他们也在过自己的人生。”**

当白苓离队后仍通过暗号和飞书维持存在，当同伴在玩家错过支线后代为处理残局，当某个曾经信任你的 NPC 因你的心境或旧事变得迟疑，玩家会感到自己的选择和缺席都被世界记住了。这种体验不靠状态栏展示，而靠延迟回响、错过的重量和重逢时的信息差建立。最理想的效果是：玩家在第二章回头想起第一章某个没有追的钩子时，不会觉得“内容过期了”，而会觉得“那个人后来怎么样了？”——这正是“活江湖”的情感核心。

## Detailed Design

### Core Rules

**1. 每个重要 NPC 使用多轴状态记录**

NPC 状态管理不把 NPC 简化成一个单一状态，而是为每个重要 NPC 同时记录多个维度：

| 维度 | 作用 | 示例 |
|---|---|---|
| 生命状态 | NPC 是否仍能参与叙事 | 存活、受伤、失踪、死亡、未知 |
| 在场状态 | NPC 当前是否可被玩家遇见 | 队内、当前场景、同城离场、远行、不可达 |
| 位置状态 | NPC 当前所在区域或叙事位置 | 江南客栈、塞北路上、未知去向 |
| 可交互状态 | 玩家当前能以何种方式接触 NPC | 可对话、只能收信、只能听传闻、锁定、不可交互 |
| 独立旅程阶段 | NPC 自己的人物弧推进到哪里 | 初遇、离队远行、调查中、代办完成、重逢 |
| 关系阶段 | 与主角的叙事关系进度 | 陌生、相识、信任、承诺、诀别 |
| 态度档位 | NPC 当前对主角的叙事态度 | 生死相托、推心置腹、以礼相待、萍水相逢、心有疑云、避而不见、闻名生惧、拔剑相向 |
| 状态标记 | 特殊剧情事实 | 已收到某封信、知道某误会、可代办某支线 |

**2. NPC 状态是叙事事实的统一来源**

对话、心境反应、感情系统、活江湖层和误会系统都应查询 NPC 状态管理，而不是各自维护一份 NPC 事实。  
例如：“白苓当前是否在江南”“谢残翁是否仍愿意见主角”“某同伴是否已经代办支线”都由本系统回答。

**3. 状态变化只由明确事件触发**

NPC 状态不会凭空变化。合法来源包括：

- 对话系统发出的 `npc_state_change`
- 主线章节推进
- 自然日事件
- 活江湖事件
- 感情系统关系节点
- 误会系统澄清或恶化事件
- 存档加载时的状态恢复

所有状态变化必须有来源标记，便于调试和叙事追踪。

**4. 独立旅程使用混合推进**

NPC 的独立旅程由两类推进共同组成：

- **剧情节点推进**：关键人物弧、重逢、离队、死亡、承诺等重大状态，只能由主线或关键剧情节点推进。
- **自然日延迟触发**：飞书到达、传闻出现、代办结果回报、短期位置变化，可由自然日系统延迟触发。

这保证角色命运不会被日历随机冲散，同时让玩家感到“你不在场时，江湖仍在走”。

**5. 错过内容采用保守代办规则**

只有被内容设计明确标记为 `delegate_allowed` 的支线或钩子，才允许被 NPC 代办。  
代办结果不自动生成，而由设计者预先配置少量结果：

- 成功代办
- 部分完成
- 失败或留下后患
- 因 NPC 当前状态不满足而无法代办

代办结果通过飞书、传闻、重逢对话或后续事件反馈给玩家。

**6. 态度档位由 NPC 状态管理保存**

NPC 状态管理保存每个重要 NPC 对主角的当前态度档位：

| 态度档位 | 含义 | 常见表现 |
|---|---|---|
| 生死相托 | 愿以性命、秘密或师门大事相托 | 关键时刻站在主角一边，触发最高信任支线 |
| 推心置腹 | 愿说真话、托付要事 | 解锁关键对话、主动飞书 |
| 以礼相待 | 态度亲近或敬重，但仍守江湖分寸 | 普通协助、语气亲近 |
| 萍水相逢 | 无明显亲疏 | 默认对话 |
| 心有疑云 | 仍愿交谈，但言辞试探 | 部分真相暂不相告 |
| 避而不见 | 不愿深谈，回避主角 | 拒绝支线、减少信息 |
| 闻名生惧 | 因主角行事、心境或旧事而畏惧 | 可能托人传话或闭门不见 |
| 拔剑相向 | 主动拒绝、阻挠、告密 | 进入冲突或敌对分支 |

态度档位可以被心境区域、善恶档位、关系阶段和误会事件影响，但本系统只保存当前结果；更细的原因链交给感情系统、误会系统和主线叙事解释。声望不直接改变单个 NPC 的态度档位，后续由活江湖层或主线叙事用于世界事件和传闻反馈。

**7. 飞书与信使系统**

飞书是 NPC 独立旅程、代办结果、求援选择和特殊信件的统一通信系统。玩家在早期主线获得默认信使“海东青”后，飞书功能正式开启；获得前不触发远程飞书，只能通过面对面对话、告示和客栈传闻获取消息。

海东青不是养成宠物，不需要喂养、照顾或升级。它是远方来信的武侠化载体：在自由活动阶段收到重要飞书时，玩家操作被短暂阻断，播放信使从屏幕外飞来、落到主角胳膊上的动画，主角自言自语提示“某人来信了”，随后进入飞书界面或特殊信件演出。

少数性格鲜明的重要角色或组织可配置“特性信使”，替代默认海东青作为专属来信标识。特性信使只影响收信动画、主角自语、玩家对来信来源的预判和信件氛围，不影响送达规则、代办成功率、求援概率、战斗或养成数值。

| 信使 | 适配对象 | 气质与用途 |
|---|---|---|
| 白鹳 | 江南水乡武林世家、水帮、跨江河势力 | 擅长长途跨江河飞行，风雨仍能赶路；一出现就有江南水汽和世家规矩感 |
| 雪雀 | 雪山门派、西域冰原宗门、清冷角色 | 耐寒、不惧暴雪；适合极寒环境中的来信，气质轻、小、孤冷 |
| 玄乌 | 邪派、幽冥杀手组织、夜行情报线 | 世人忌讳，不易被拦；夜间传密信，天然带不祥和秘密感 |
| 灵鹤 | 隐世仙门、医者、高人、寻人线 | 传说通灵，能自主寻人；适合“你本不该收到，却偏偏送到了”的信 |
| 苍鹰 / 黄鹰 | 名门密探、王府暗探、山林急报 | 野性强，视力锐，避网穿林；适合加急、绝密、带危险气息的情报 |

所有飞书统一归档到飞书入口，按角色或组织分类显示；有未读信件时显示未读标记。主角收到不同角色、不同信件类型时的自言自语应有所区别，具体文案由后续叙事写作阶段打磨。

**8. 代办飞书与求援飞书**

高质量支线如果玩家没有亲自进入，可以通过代办飞书维持阶段性存在感。队友代办过程中，内容设计可预设若干封阶段信件：

- **启程信**：队友说明已接下此事，正往某地去。
- **进展信**：汇报途中见到的人、物或阻碍，让支线气味浮出水面。
- **见闻信**：分享地方传闻、人物侧写或江湖细节，强调“支线仍在江湖里发生”。
- **结果信**：报告代办成功、部分成功、失败或留下后患。

求援飞书只发生在支线开始之前、代办正式结算之前。若玩家派遣的队友能力低于任务基线，且该任务标记为 `help_request_allowed`，系统可根据能力差距和态度档位触发求援。触发后玩家选择：

- **亲自前往**：主角接手，完整走一遍该支线。
- **回信指点**：提高本次代办的临时能力值，但任务仍可能失败。
- **暂不理会**：队友按原能力继续代办，可能成功也可能失败。

求援不是随机支线生成器；所有求援内容必须由内容设计预写。态度越亲近，队友越愿意开口求助；态度低时可能硬撑、沉默，最终以失败或后患形式回报。

### States and Transitions

| 状态变化 | 触发条件 | 结果 |
|---|---|---|
| 在场 → 离场 | 剧情离队、章节转场、独立旅程开始 | NPC 不再出现在当前场景，可能转为飞书或传闻联系 |
| 离场 → 来信 | 自然日延迟事件触发 | 对话系统生成 Letter 节点，飞书进入角色归档 |
| 代办中 → 求援 | 支线允许求援，队友能力低于任务基线，且态度允许开口 | 触发求援飞书，玩家选择亲自前往、回信指点或暂不理会 |
| 离场 → 代办中 | 玩家错过可代办支线，且 NPC 状态满足代办条件 | 记录代办任务，等待后续剧情节点或自然日结算 |
| 代办中 → 代办完成 | 到达配置的结算日或章节节点 | 产生结果标记，并触发飞书、传闻或重逢反馈 |
| 离场 → 重逢 | 主线节点、场景解锁或关系节点触发 | NPC 重新变为可对话，并携带离场期间的旅程结果 |
| 可对话 → 锁定 | 战斗、过场、锁定对话、剧情禁用 | 暂时不可交互 |
| 任意 → 死亡 | 剧情死亡事件触发 | NPC 永久不可对话，相关支线进入死亡分支或关闭 |
| 态度变化 | 心境区域、善恶档位、误会或关系事件改变 | 更新态度档位，影响后续对话路由 |
| 飞书排队 → 送达 | 阻断状态结束后，玩家进入自由活动并走出配置步数 | 播放信使送信演出，进入飞书界面或特殊信件展示 |

### Interactions with Other Systems

| 系统 | 方向 | 接口 |
|---|---|---|
| 对话系统 | 对话 → NPC | `npc_state_change(npc_id, field, value, source_event)` |
| 对话系统 | NPC → 对话 | 查询 NPC 当前在场、可交互、态度档位、旅程阶段，以选择对话序列 |
| 心境双轴 | 心境 → NPC | 使用 `get_mindset_zone()`、`get_morality_tier()` 影响 NPC 态度档位 |
| 角色属性 / 功力 | 属性 → NPC | 提供队友能力值，用于求援触发和回信指点后的代办能力判定 |
| 感情系统 | 双向 | 感情系统读取关系阶段和态度档位；关键关系节点可更新 NPC 旅程阶段 |
| 自然日 + 体力 | 日历 → NPC | 推进书信到达、短期远行、代办结算等延迟事件 |
| 活江湖层 | 双向 | 活江湖层读取 NPC 状态生成传闻；也可写入 NPC 的世界事件结果 |
| 误会系统 | 误会 → NPC | 误会生成、恶化、澄清时更新态度档位或状态标记 |
| 主线叙事 | 主线 → NPC | 章节节点推进 NPC 旅程阶段、生死、位置和重逢 |
| 存档系统 | 双向 | 持久化每个重要 NPC 的多轴状态、状态标记、代办任务和最近状态变更记录 |

> 注：当前 review mode 为 `lean`，本节未调用专家代理；后续 `/design-review` 应重点检查状态轴是否过多、态度档位是否和心境/感情系统职责重叠。

## Formulas

### F1. NPC 态度档位判定

The `npc_attitude_score` formula is defined as:

`npc_attitude_score = clamp(base_attitude + mindset_mod + morality_mod + misunderstanding_mod, -4, +3)`

**Variables:**

| Variable | Symbol | Type | Range | Description |
|---|---|---|---|---|
| 基础态度 | `base_attitude` | int | -2 到 +2 | 由当前关系阶段给出；关系越深，基础态度越高 |
| 心境修正 | `mindset_mod` | int | -1 到 +1 | NPC 对当前 `MindsetZone` 的反应；兼容 +1，不兼容 -1，普通 0 |
| 善恶修正 | `morality_mod` | int | -1 到 +1 | NPC 对当前善恶档位的反应；侠义 NPC 厌恶极恶，邪派 NPC 可能欣赏狠辣 |
| 误会修正 | `misunderstanding_mod` | int | -2 到 0 | 当前存在误会时施加负修正；无误会为 0 |

**Output Range:** -4 到 +3。输出映射为态度档位：

| 分数 | 态度档位 | 含义 |
|---|---|---|
| +3 | **生死相托** | 愿以性命、秘密或师门大事相托；关键时刻会站在主角一边 |
| +2 | **推心置腹** | 愿说真话、托付要事，重逢时少有隐瞒 |
| +1 | **以礼相待** | 态度亲近或敬重，但仍守江湖分寸 |
| 0 | **萍水相逢** | 无明显亲疏，按常规身份和场合应对 |
| -1 | **心有疑云** | 仍愿交谈，但言辞试探，部分真相暂不相告 |
| -2 | **避而不见** | 不愿深谈，回避主角，支线或隐情被锁住 |
| -3 | **闻名生惧** | 因主角行事、心境或旧事而畏惧，可能托人传话或闭门不见 |
| -4 | **拔剑相向** | 主动拒绝、阻挠、告密，甚至进入冲突或敌对分支 |

**Example:** 白苓当前基础态度为“推心置腹” `+2`，心境兼容 `+1`，善恶中性 `0`，无误会 `0` → `clamp(2+1, -4, +3)=+3` → 态度档位为“生死相托”。

### F2. 代办资格判定

The `delegate_eligible` formula is defined as:

`delegate_eligible = delegate_allowed AND npc_available AND relationship_ok AND journey_stage_ok AND NOT blocking_flag`

**Variables:**

| Variable | Symbol | Type | Range | Description |
|---|---|---|---|---|
| 支线允许代办 | `delegate_allowed` | bool | true/false | 内容设计是否明确标记该支线可被代办 |
| NPC 可用 | `npc_available` | bool | true/false | NPC 未死亡、未锁定、未处于不可达状态 |
| 关系满足 | `relationship_ok` | bool | true/false | NPC 当前关系阶段或态度档位达到该代办所需门槛 |
| 旅程阶段满足 | `journey_stage_ok` | bool | true/false | NPC 当前独立旅程阶段允许接手该类事件 |
| 阻断标记 | `blocking_flag` | bool | true/false | 是否存在剧情阻断，例如误会未解、主线冲突、NPC 正在执行更高优先级任务 |

**Output Range:** 布尔值。`true` 表示可以进入“代办中”；`false` 表示该错过内容保持错过、过期或等待其他系统处理。

**Example:** 某江南支线 `delegate_allowed=true`，沈夜雪正在远行但可用，关系为“以礼相待”，旅程阶段为调查中，且无阻断标记 → `delegate_eligible=true` → 可进入“代办中”。

### F3. 独立旅程触发判定

The `journey_trigger_ready` formula is defined as:

`journey_trigger_ready = chapter_condition_met OR day_delay_met`

**Variables:**

| Variable | Symbol | Type | Range | Description |
|---|---|---|---|---|
| 章节条件满足 | `chapter_condition_met` | bool | true/false | 主线或关键剧情节点已到达 |
| 自然日延迟满足 | `day_delay_met` | bool | true/false | 当前游戏日已达到配置的触发日 |
| 触发优先级 | `trigger_priority` | enum | critical/normal/flavor | 若多个触发同时满足，用优先级决定处理顺序 |
| 已触发标记 | `already_triggered` | bool | true/false | 同一旅程事件是否已经触发过 |

最终执行条件为：

`journey_event_fires = journey_trigger_ready AND NOT already_triggered`

**Output Range:** 布尔值。`true` 表示触发书信、传闻、位置变化、代办结算或重逢事件；`false` 表示等待后续章节或自然日。

**Example:** 白苓离队后配置“第 3 日来信”，当前已到第 3 日，且该信未触发过 → `day_delay_met=true`，`already_triggered=false` → 触发飞书事件。

### F4. 求援飞书触发判定

The `help_request_chance` formula is defined as:

`help_request_chance = clamp(base_help_chance + ability_gap_mod + attitude_mod, 0, 100)`

**Variables:**

| Variable | Symbol | Type | Range | Description |
|---|---|---|---|---|
| 基础求援概率 | `base_help_chance` | int | 0 到 100 | 由支线配置；未标记 `help_request_allowed` 的支线固定为 0 |
| 能力差距修正 | `ability_gap_mod` | int | 0 到 +40 | 队友能力低于任务基线越多，修正越高；能力足够时为 0 |
| 态度修正 | `attitude_mod` | int | -30 到 +30 | 态度越亲近越愿意求助；态度低时更可能硬撑而不求援 |

**Output Range:** 0 到 100。只有当支线标记 `help_request_allowed=true`，且求援发生在代办正式展开前，才进行此判定。

**Example:** 某支线基础求援概率 20，队友能力明显不足 `ability_gap_mod=30`，态度为“推心置腹” `attitude_mod=20` → `clamp(20+30+20, 0, 100)=70` → 有 70% 概率触发求援飞书。

### F5. 回信指点加成

The `guided_delegate_power` formula is defined as:

`guided_delegate_power = delegate_power + guidance_bonus`

**Variables:**

| Variable | Symbol | Type | Range | Description |
|---|---|---|---|---|
| 队友代办能力 | `delegate_power` | int | 0 到 100 | 队友当前用于该任务的能力评估，来源由角色属性 / 功力系统定义 |
| 回信指点加成 | `guidance_bonus` | int | +5 到 +20 | 玩家选择“回信指点”后给予本次代办的临时加成 |
| 任务基线 | `task_baseline` | int | 0 到 100 | 该支线代办所需的推荐能力值 |

**Output Range:** 0 到 120。此值只影响本次代办判定，不永久提升队友能力。即使 `guided_delegate_power >= task_baseline`，任务也可能因剧情配置进入“部分成功”或“留下后患”。

**Example:** 队友代办能力 45，任务基线 60，玩家回信指点提供 +15 → `guided_delegate_power=60`。该任务达到基线，但最终结果仍按支线预设分支结算。

### F6. 排队飞书送达判定

The `queued_letter_delivery_ready` formula is defined as:

`queued_letter_delivery_ready = free_roam_active AND steps_after_unblock >= queued_letter_step_delay`

**Variables:**

| Variable | Symbol | Type | Range | Description |
|---|---|---|---|---|
| 自由活动中 | `free_roam_active` | bool | true/false | 玩家已离开战斗、锁定对话、CG 或过场，可被轻度打断 |
| 阻断后步数 | `steps_after_unblock` | int | 0+ | 阻断状态结束后玩家累计走出的步数 |
| 排队飞书步数延迟 | `queued_letter_step_delay` | int | 4 到 20 | 信件排队后需要玩家走出多少步才触发送达，默认建议 8-12 |

**Output Range:** 布尔值。`true` 表示播放信使送信演出；`false` 表示继续排队。

**Example:** 玩家刚结束锁定对话，飞书在队列中等待。配置步数延迟为 10，玩家走出第 10 步时 → `queued_letter_delivery_ready=true` → 海东青或特性信使飞来送信。

> 注：当前 review mode 为 `lean`，本节未调用 `systems-designer`；本节采用轻量叙事判定，后续独立 `/design-review` 应重点检查这些公式是否足够可实现且不过度数值化。

## Edge Cases

- **If NPC 已死亡但还有未触发的飞书事件**：取消所有未触发的普通飞书；若该飞书是死亡前已写好、具有关键叙事价值的“遗书”，必须由内容设计显式标记为 `posthumous_allowed`，才允许在死亡后送达。

- **If NPC 已死亡但仍有关联支线处于“代办中”**：立即终止代办任务，并按“代办失败”处理。不得让死亡 NPC 完成新行动，也不自动转交给其他 NPC。

- **If NPC 处于“失踪”或“未知去向”状态**：允许传闻继续出现，但禁止直接对话、主动来信和代办新任务；只有标记为“失踪期间可触发”的预设事件可以发生。

- **If 同一天多个 NPC 旅程事件同时满足触发条件**：按优先级处理：`critical` > `normal` > `flavor`。同优先级事件按内容配置顺序处理；若多个事件会改写同一 NPC 的同一状态字段，只执行优先级最高者，其余事件延迟到下一自然日重新判定。

- **If 主线关键剧情与支线代办结果冲突**：主线关键剧情优先。代办结果改为“被主线中断”，并通过飞书、传闻或重逢对话解释原因，避免玩家感觉事件凭空消失。

- **If 对话进行中收到 NPC 状态变化事件**：遵守对话系统规则，状态变化排队到当前对话结束后批量生效。当前对话使用进入对话前锁定的 NPC 状态，避免对话中途路由变化。

- **If 心境区域、善恶档位或误会导致 NPC 态度档位变化**：态度更新不打断当前交互；从下一次对话序列选择开始生效。若这是关键转折，内容设计应安排一段明确的重逢或对峙对话承接变化。

- **If NPC 当前状态不满足代办资格，但支线即将过期**：不强行代办。该支线按配置进入“错过”或“过期后果”分支。Content Overflow Principle 不等于所有内容都必须被保存。

- **If 玩家在同一时间触发多个可代办支线，而同一 NPC 只能处理一个**：使用支线优先级决定接手顺序；未被接手的支线保持可由玩家处理、由其他 NPC 处理，或自然过期。禁止一个 NPC 同时进入多个互斥代办任务。

- **If 存档加载后 NPC 状态字段缺失或非法**：使用默认安全值恢复：生命状态=未知，在场状态=不可达，可交互状态=不可交互，态度档位=萍水相逢，并记录警告日志。不得因单个 NPC 状态损坏导致读档失败。

- **If NPC 态度分数超过公式上下限**：通过 `clamp(..., -4, +3)` 钳位到合法范围。触顶或触底不额外触发事件，只改变最终态度档位。

- **If 某 NPC 没有配置心境态度表**：`mindset_mod=0`，并在内容验证中报 warning。不能因为缺表导致 NPC 消失或对话不可进入。

- **If 误会系统尚未实现但已有误会标记**：`misunderstanding_mod=0`，误会标记仅作为状态事实保存，不影响态度档位；待误会系统 GDD 完成后再启用修正。

- **If 玩家尚未通过主线获得海东青**：不触发远程飞书和信使送信演出。相关信息只能通过面对面对话、告示、客栈传闻或主线事件传达；已排队飞书等待飞书功能开启后再按规则送达。

- **If 飞书到达时玩家处于战斗、锁定对话、CG、过场或限时主线段**：飞书进入待送达队列，不立即打断。阻断结束后，玩家进入自由活动并走出配置步数，才触发信使送信演出。

- **If 玩家阻断结束后一直不移动**：飞书保持排队。若玩家切换场景、进入客栈休息或触发新的自由活动节点，系统可将其视为兜底送达点，播放信使送信演出。

- **If 多封飞书同时排队**：按信件优先级处理：特殊信件 > 求援飞书 > 结果信 > 进展/见闻信 > 普通信。一次送信演出最多打开一封高优先级信；其余信件进入飞书入口并显示未读标记，避免连续打断玩家。

- **If 求援飞书到达后玩家选择“亲自前往”**：该代办任务转为主角亲自处理，完整进入该支线；原队友代办结算取消，不再自动生成代办结果。

- **If 求援飞书到达后玩家选择“回信指点”**：只为本次代办增加临时能力值，不保证成功。任务仍按预设代办结果结算。

- **If 求援飞书到达后玩家选择“暂不理会”或长期不读**：队友按原能力继续代办；若支线到达结算节点，未读求援信不阻止失败或后患发生。

- **If 队友态度过低但能力不足**：可以不触发求援飞书，表现为队友硬撑或沉默。失败后通过结果信、传闻或重逢对话反馈，不 retroactively 给玩家求援机会。

- **If 特性信使未配置**：使用默认海东青送信演出。信件归档、未读标记和送达规则不受影响。

- **If 特殊信件是遗书或血书**：收到时可绕过普通飞书入口，在屏幕中心缓慢展开；读完后仍归档到飞书入口，供玩家回看。

## Dependencies

NPC 状态管理是 Foundation/Core 层系统，本身不依赖其他系统才能存在，但会读取多个系统的事件或查询结果来更新 NPC 当前事实。它的主要职责是成为“NPC 当前事实”的统一来源，而不是替代对话、心境、感情或活江湖层。

| 系统 | 方向 | 依赖性质 | 硬/软 |
|---|---|---|---|
| **对话系统** | 双向 | 对话系统可发送 `npc_state_change` 更新 NPC 状态；进入对话前查询 NPC 当前状态以选择对话序列；飞书正文、求援选择、特殊信件展示复用对话/信件节点 | 硬 |
| **存档系统** | 双向 | NPC 多轴状态、状态标记、代办任务、飞书归档、未读标记、待送达队列、最近状态变更记录必须持久化 | 硬 |
| **心境双轴** | 心境 → NPC | NPC 状态管理读取 `MindsetZone`、善恶档位来计算态度档位；心境不直接写 NPC 状态 | 硬（态度计算） |
| **角色属性 / 功力** | 属性 → NPC | 队友代办能力和任务基线比较用于求援飞书、回信指点和代办结果判定 | 硬（求援/代办） |
| **主线叙事 / 章节推进** | 主线 → NPC | 主线节点推进 NPC 生死、位置、离队、重逢、关键旅程阶段；早期主线授予海东青并开启飞书功能 | 硬（关键剧情） |
| **地图 / 场景管理** | 场景 → NPC | 场景加载时根据 NPC 位置和在场状态决定是否生成 NPC 实体；飞书排队送达需要知道玩家是否处于自由活动 | 硬（场景呈现） |
| **自然日 + 体力** | 日历 → NPC | 自然日触发飞书到达、短期远行、代办结算等延迟事件 | 软（VS 可先做最小子集） |
| **感情系统（彗星模型）** | 双向 | 感情系统读取关系阶段和态度档位；关键感情节点可写入旅程阶段、可交互状态、特性信使或状态标记 | 软（系统未设计） |
| **活江湖层** | 双向 | 活江湖层读取 NPC 状态生成传闻和世界事件；也可写入预设事件结果 | 软（Alpha） |
| **误会系统** | 误会 → NPC | 误会生成、恶化、澄清时写入状态标记或态度修正来源 | 软（Alpha） |
| **朦胧化 UI** | NPC → UI | 飞书统一入口、角色归档、未读标记、信使送达提示和特殊信件展开由 UI 系统呈现 | 软 |

**依赖优先级**

当多个系统试图影响同一 NPC 状态时，按以下优先级处理：

1. 主线叙事 / 章节推进
2. 生命状态变化
3. 当前锁定对话或过场
4. 感情关键节点
5. 误会澄清或恶化
6. 自然日事件 / 活江湖事件
7. 飞书进展、见闻和 flavor 传闻

**接口所有权声明**

- NPC 状态管理拥有：NPC 生死、位置、在场状态、可交互状态、独立旅程阶段、关系阶段、态度档位、状态标记、代办任务状态、飞书归档、飞书送达队列、信使类型。
- 对话系统拥有：对话图、节点条件、对话文本、信件正文、求援选择文本。
- 心境双轴拥有：`MindsetZone`、善恶档位、声望和结局判定。
- 角色属性 / 功力拥有：队友能力值、任务基线的属性解释。
- 感情系统拥有：好感变化、承诺选择、伴侣结局。
- 活江湖层拥有：世界事件调度、传闻池、江湖反馈。
- 误会系统拥有：误会产生、误会透明度、澄清路径。
